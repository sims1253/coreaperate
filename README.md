# Coreaperate 0.1

An experimental two-person, MIDI-first REAPER companion. Each person runs a local REAPER project and owns different tracks. A Python coordinator accepts owned-track edits; deferred Lua scripts observe native edits and apply accepted changes in place.

**Use disposable copies. This is a runnable prototype, not a fully accepted release.** Python/WebSocket/SQLite tests, cross-language file-spool tests, and a real REAPER adapter smoke test passed on Windows. A manual two-instance trial confirmed basic MIDI synchronization, ownership enforcement, and explicit restoration after an unauthorized edit. The complete acceptance checklist remains outstanding. See [test evidence](docs/TESTING.md) for the exact boundary. No latency, uninterrupted-playback, macOS, or Linux success is claimed.

**Native Undo/Redo is project-wide and is not collaborative undo.** Use **Undo my last shared edit** in the panel. We cannot disable or reliably identify all native Undo paths. Native changes are checked like other edits: an unowned-track change pauses synchronization and preserves local work. A supported change on an owned track can look like an ordinary new edit, including when native Undo caused it.

## What is implemented

- Exactly two authenticated identities; host participates by running the same `join` client as the guest.
- Shared track name, volume, pan; MIDI item create/move/right-trim/delete; note pitch, onset, duration, velocity, channel, and note mute. Notes beyond an item's right edge stay in the shared model.
- Coordinator-owned claim/release/handover; revisions per track, epochs, ordered session sequence, replay, durable deduplication, and scoped inverse undo.
- Stock deferred Lua/gfx bridge, automatic observation (150 ms scan + 150 ms settling), immutable file-spool IPC, acknowledgements, local exports, explicit restoration, and visible pause states.
- REAPER project handle binding; persistent baseline/accepted metadata; stable track GUIDs and item/take extension IDs; native copy detection; collision and unsupported-content checks.

Playback, edit cursor, selection, editors, track/item audition mute and solo, record arm, monitoring, and master choices are local. **FX, samples, plugin presets, and audio assets are not synchronized. Matching canonical edit state does not certify identical audio output.** Configure matching instruments before copying the baseline. The demo uses stock ReaSynth on both tracks: it is a pitched rhythmic demo, not a drum-kit emulation.

## Install (Windows PowerShell)

Use REAPER **7.79** and Python **3.11+**. Development used Python **3.13.13**, REAPER **7.79/x64**, and Windows 11 build **26200**. Older REAPER versions are not supported by this initial setup; `InsertTrackInProject` must be available.

From the repository directory:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
.\.venv\Scripts\python -m pytest -q
.\.venv\Scripts\python -m coreaperate init --directory runtime/session
```

For runtime only, install with `python -m pip install -e .` in your virtual environment. Python's only runtime dependency is `websockets==17.0.1`; SQLite and asyncio are standard library modules. Lupa is a **test-only** Lua runtime, not a REAPER dependency. Pins are in [pyproject.toml](pyproject.toml) and [requirements-dev.txt](requirements-dev.txt). Lua dkjson 2.5 is vendored with its MIT license and a recorded SHA-256. Dependency licenses are in [licenses](licenses).

For macOS/Linux (implementation intended to be portable, **not tested**):

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
.venv/bin/python -m coreaperate init --directory runtime/session
```

Use `.venv/bin/python` for the remaining commands on those platforms. Paths in REAPER dialogs must be absolute.

## Prepare the demo baseline

For a quicker **Windows-only** trial, this repository includes `examples/prepared-demo.rpp` and `examples/prepared-demo.baseline.json`, generated by the successful real REAPER smoke run. Copy the `.rpp` into two independent local files, use that JSON with `host --baseline`, and skip preparation. Do not run preparation on this already-prepared example. Its stock ReaSynth reference is Windows-specific; on other platforms create a new baseline with the scripts below. No participant identity or credential is embedded in the example.

1. In REAPER, create a **new empty disposable project**. Do not run demo/probe scripts on your real music.
2. Open **Actions → Show action list → New action → Load ReaScript**. Load `reaper/demo.lua`, `prepare.lua`, `bridge.lua`, `create_item.lua`, `probe.lua`, `smoke.lua`, and `restore_export.lua` as separate scripts. Keep the `lib` folder beside them.
3. Run `demo.lua`. It creates Drums and Bass with ReaSynth and short MIDI patterns. Enable your normal audio device manually and audition it at a comfortable monitoring level.
4. Save As `<repo>/runtime/demo.rpp`. Run `prepare.lua`. It exports a live recovery copy, validates the restricted format, writes persistent collaboration metadata, saves the baseline, and writes `runtime/demo.rpp.baseline.json`. **Do not run preparation again on either participant's working copy.** If validation fails, repair the disposable project before retrying; exports are retained.
5. Close the prepared project. Make two independent local copies:

```powershell
Copy-Item runtime/demo.rpp runtime/A.rpp
Copy-Item runtime/demo.rpp runtime/B.rpp
```

This is the only bootstrap `.rpp` copy. Never sync, repeatedly reload, or overwrite live working `.rpp` files.

Preparation accepts 1–16 pre-created flat stereo tracks, up to 128 MIDI items total (64 per track), 4096 notes total (2048 per item), and a canonical project under 512 KiB. Tempo must be fixed with **no tempo/time-signature markers**. No sends, folder structure, lanes, or track automation envelopes. Use normal stereo balance pan mode and default stereo master routing.

Items must have one MIDI take, play rate 1, source offset 0, **Loop source off**, no take FX, and default take pitch/volume/pan. Unique source-pool GUIDs are required. REAPER stores a pool GUID even on an ordinary source; duplicate source GUIDs are rejected. Keep the project playback rate at 1.

## Start two local instances

Run three terminals in the repository:

```powershell
# Terminal 1: coordinator (loopback only by default)
.\.venv\Scripts\python -m coreaperate host --baseline runtime/demo.rpp.baseline.json --credentials runtime/session/credentials.local.json --database runtime/session/coordinator.sqlite
```

```powershell
# Terminal 2: host musician A, using the ordinary client protocol
.\.venv\Scripts\python -m coreaperate join --config runtime/session/A.local.json
```

```powershell
# Terminal 3: guest musician B
.\.venv\Scripts\python -m coreaperate join --config runtime/session/B.local.json
```

Open `runtime/A.rpp` and `runtime/B.rpp` in **separate REAPER processes**, not two tabs sharing the same IPC directory. On Windows, REAPER's `-newinst` switch launches an additional process:

```powershell
& 'C:\Program Files\REAPER (x64)\reaper.exe' -newinst "$PWD/runtime/A.rpp"
& 'C:\Program Files\REAPER (x64)\reaper.exe' -newinst "$PWD/runtime/B.rpp"
```

In each instance, open **Actions → Show action list**, choose the **Main** section, and use **New action → Load ReaScript** to add `reaper/bridge.lua` if it is not listed. Then select **Script: bridge.lua** and click **Run**; loading it only registers the action. Enter the absolute paths `<repo>/runtime/session/A` and `<repo>/runtime/session/B`, respectively. Each IPC folder binds to that working project's path. Only one bridge and one companion may use each folder. A companion OS lock rejects a second companion. If you move/rename a project, create a new local IPC folder and update its private config; do not repoint a live folder.

The bridge checks the prepared session/baseline through the companion, then reconciles current live state against the accepted checkpoint. Selecting another REAPER tab never changes the bridge's bound project. Closing the bound project stops its bridge; the companion may need restarting before a new bridge session.

## Ownership and editing

Click a track row **inside the Coreaperate panel**, so the `>` marker moves beside the intended track. Selecting a track in REAPER itself does not choose the panel's target. A selects the panel's Drums row and clicks Claim; B selects its Bass row and clicks Claim. Wait for the owner and revision display to acknowledge the claims. Edit notes using the ordinary MIDI editor, drag items, adjust right edges, and change owned-track name/volume/pan. No Publish button is needed.

For new items, use `create_item.lua` on the selected owned track, or ensure REAPER's native creation produces **non-looping** MIDI items. The helper creates a four-QN item at the local cursor and does not bypass synchronization checks. REAPER normally allows source looping; an item created with looping enabled deliberately pauses the bridge. Do not left-trim, slip-edit, stretch, pool, record, or move items across tracks.

Wait until no changes are pending before **Release**, **Hand over**, or **Undo my last shared edit**. These controls refuse while the local track differs from accepted state. Handover targets the other generated identity (A/B). Reservations survive disconnect and coordinator restart; there is no expiry or stealing. Reconnect with the owner's retained private credential to release/hand over a reserved track.

The undo action reverses your latest eligible musical operation only if its track revision is still current and you own the track. The other person's track is untouched. Bursts can produce several operations (properties first, item deletions, then item replacements); one scoped undo reverses **one accepted operation**, not an entire native drag/edit gesture. Repeated undo of an already-undone edit and stale inverses are refused. Redo is not implemented.

## Two computers / private LAN

Keep the coordinator and A's client on the host. Explicitly opt into a LAN bind with `--bind 0.0.0.0`. Plain `ws://` has **no transport encryption**; use only localhost or an explicitly trusted/encrypted private-network test environment. Do not port-forward this prototype or expose it to the public internet.

Transfer only the prepared baseline `.rpp` and B's generated `B.local.json` to your friend through a trusted method. Do not send `credentials.local.json` or A's config. On B's computer edit B's private JSON: set `url` to `ws://HOST_PRIVATE_ADDRESS:8765` and `ipc` to an absolute **local** directory outside Syncthing. Retain B's generated token and client name. Install this repository and run `join --config /absolute/path/B.local.json`; it creates the nonsecret bridge configuration and spool directories. Open B's independent baseline copy, run `bridge.lua`, and enter that IPC directory.

No code changes your firewall, Syncthing settings, or router. Credentials stay outside projects and are never intentionally logged. Protect local config files and disk access; the spool is local-trust IPC, not a sandbox against another process running as you.

## Pause, reconnect, and recovery

An unowned edit, unsupported content/structure, failed apply verification, or lost heartbeat pauses publication. The implementation conservatively pauses the **whole session on that client**, even for a single affected track. It never automatically merges an offline branch or restores over local divergence. The companion does not automatically reconnect. Press **Connect** after reviewing the state.

Accepted coordinator state, live local state, and one in-flight operation per track are separate. A self-echo updates accepted state without overwriting newer local edits. Old spool proposals on a new connection are queried for their stored outcome; unaccepted ones are rejected as local branches, not newly published. Sequence gaps request history replay.

On a clean save/close/reopen, the project retains its accepted musical checkpoint. If live data equals that checkpoint, a newer coordinator snapshot may be applied after checks. If live data already equals the snapshot, no application is needed. Other differences pause with an actionable recovery message. A snapshot alone does not authorize overwriting local edits.

Use these recovery choices:

1. **Export live recovery** preserves the current unsaved track chunks (including unsupported MIDI and local FX references), the canonical data when readable, and the accepted state in an immutable local JSON file. Export files are under `<ipc>/recovery/`. No branch/backup cleanup runs automatically.
2. To retain that work as music, open an **empty disposable project**, run `restore_export.lua`, choose the export by absolute path, confirm, and Save As a separate local `.rpp`. This imports local track chunks; it is never a network operation. It cannot reconstruct missing external plugins or media and does not import project-global settings. Use the prepared baseline's fixed tempo/meter when listening to the branch.
3. To abandon the divergent shared edits in the current project, first **Pause**, then **Restore accepted…**. It creates another live export and asks for explicit confirmation before targeted restoration. It restores the last received snapshot when reconciliation failed, otherwise the last accepted state. It cannot repair unsupported content/structure: preserve the branch and reopen an appropriate prepared/checkpoint copy instead.
4. Press **Connect** to fetch and verify current authoritative state. If unresolved in-flight proposals remain, export first, stop/restart the bridge and companion, and reconnect to query their outcomes. A second reconciliation may be necessary after the coordinator advanced during recovery.

Save both local projects normally once pending edits drain. SQLite WAL/history is durable before an accepted response. Keep the database, WAL/SHM files, credentials, and baseline JSON together for coordinator recovery. Do not delete a database to solve divergence: that discards authority/history. Power-loss durability of Lua's file flush/rename and unsaved REAPER extension state is **not** equivalent to SQLite durability; after a crash, reconciliation may require an explicit branch recovery.

## Syncthing boundary

Recommended layout:

```text
local-only/
  A.rpp or B.rpp
  recovery/
  session/       # configs, tokens, IPC, SQLite, recovery exports
shared-assets/   # optional Syncthing area: existing media + intentionally published checkpoints
```

No live `.rpp` merge, shared writable project, database sync, or spool sync. Asset discovery/transfer is reserved for a later module; current canonical items contain no file paths and no audio subsystem. See [Syncthing's synchronization model](https://docs.syncthing.net/users/syncing.html).

## Unsupported and remaining limitations

- CC, SysEx, text, notation/other MIDI metadata, nonzero note-off velocity, and unpaired raw events cause an explicit unsupported state. Data is not stripped. Only a narrowly recognized final REAPER source-end CC123 marker and empty source bookkeeping records are excluded from the note model.
- No same-track concurrent editing, offline merging, leases, routing edits, automation, recording, audio items, tempo changes, track creation/deletion/reorder, pooling, take FX, stretch/source offsets, plugin-state sync, streaming, NAT traversal, or accounts.
- Exact unchanged notes retain receiver selection. Unambiguous changed notes also carry their receiver selection through replacement. Ambiguous duplicate notes or simultaneous edits changing every identifying property may lose selection; stock note events do not expose persistent IDs. This remains an acceptance limitation, along with unverified editor/scroll/playback behavior in the complete two-instance workflow. Item/track objects are preserved for property edits and moves.
- Observation, raw event inspection, and recovery chunk exports still perform bounded-by-project-size work in the callback. No sub-second latency or worst-case callback-time guarantee has been measured. Do not use large plugin states or exceed the prototype limits.
- A hard failure during an apply can leave partial local changes. Publication stops; the pre-apply live export is the recovery source. No success acknowledgement is recorded by the bridge until state verification succeeds.
- Use A/B generated identities with panel handover. The lower-level protocol supports registered identifiers, but the panel's handover shortcut is deliberately two-name specific.
